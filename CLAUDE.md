## Project

`connectflow` — a TanStack Start (React 19 + Vite) app deployed to Cloudflare Workers, backed by Neon Postgres via Drizzle, with Better Auth for authentication. Scaffolded by `create-tanstack` (see `.cta.json` for the enabled add-ons). Most of the app is still starter code; `README.md` is the generator's boilerplate, not a description of this app.

## Commands

Package manager is **pnpm** (enforced by `pnpm-workspace.yaml` build allowlist).

```bash
pnpm dev              # vite dev on port 3000
pnpm build            # vite build
pnpm deploy           # build + wrangler deploy
pnpm check            # biome lint + format check (use before finishing work)
pnpm lint / format    # biome individually; `biome check --write` to auto-fix
pnpm generate-routes  # tsr generate — regenerate src/routeTree.gen.ts
pnpm db:generate      # drizzle-kit generate (SQL migrations into ./drizzle)
pnpm db:push          # push schema straight to the DB (dev shortcut)
pnpm db:migrate       # apply generated migrations
pnpm db:studio        # drizzle studio
pnpm dlx shadcn@latest add <component>   # add a shadcn/ui component
```

```bash
pnpm test             # vitest run
pnpm test:watch       # vitest
```

Tests are **Vitest**. `*.test.ts` are pure and always run; `*.integration.test.ts` hit the real `DATABASE_URL` and skip when it is unset. Integration tests namespace their fixtures and tear them down — they run against the dev database, so they must never leave rows behind.

TypeScript has no `typecheck` script; run `pnpm exec tsc --noEmit` to type-check.

## Architecture

### Members and scoping
`members` is a single self-referencing table: a connect leader **is** a member, and `members.leaderId` points at another member row. The "Leader" badge in the members table means *tree position* (someone reports to you) — it is not the account's admin/leader access level.

A leader's login account is tied to their member row by `members.userId`. That link is what scopes them: they see members whose `leaderId` is one of their own member rows, direct reports only (never recursive). **A leader with no linked member row sees nothing** — `features/members/scope.ts` is the single place that decides this, and it must never fall through to "no filter", which would show one leader the entire membership. Both `member-list/query.ts` and `member-stats/query.ts` apply that predicate in SQL; never fetch and filter in a component.

Deleting a member who leads people is refused with a message telling the caller to reassign first — never cascaded, never orphaned. The `restrict` foreign key is the backstop.

**CSV import** (`features/members/import-csv/`) reads the connect-database export: `Name and Surname Of Leader` / `Connect Members`, with the leader column forward-filled down each group. Two passes in one transaction — insert everyone unlinked, then resolve leader names.

A leader named in the file with **no member row of their own** (the top of the tree) is *created* as a member, not rejected — a leader is a member, so there is only one reading — and is reported back in the result. Only a name matching **several** members is a genuine guess: that halts and rolls back the whole import, inserts included. Add new header spellings to `HEADER_ALIASES` in `parse-csv.ts`; `name` is matched before `leaderLabel` so "Connect Members" binds to the member column rather than the leader column's "connect" alias.

**Drizzle gotcha:** inside a raw ``sql`` `` template, `${members.id}` renders as a bare `"id"`, so a correlated subquery resolves it against *its own* table. Write `${members}.id` instead. This silently returned zero from a `count(*) filter (where exists ...)` until an integration test caught it.

### Dashboard shell
`_authed.tsx` is both the auth guard and the layout: it renders `SidebarProvider` → `AppSidebar` → `SidebarInset` → `Outlet`, following the shadcn `dashboard-01` block. Pages nested below render their own `<SiteHeader title=... actions=... />` as their first element. Sidebar entries for sections that have no route yet are rendered disabled rather than as links, so nothing 404s.

`TooltipProvider` is mounted in `__root.tsx` — `SidebarMenuButton`'s `tooltip` prop throws without it.

### Routing and rendering
File-based routing under `src/routes/`, with `src/routeTree.gen.ts` **generated** (regenerated by the Vite plugin during `dev`/`build`; never hand-edit — it's marked readonly in `.vscode/settings.json` and excluded from Biome).

- `src/routes/__root.tsx` is the document shell (`shellComponent`) — `<html>`/`<head>`/`<body>`, `HeadContent`, `Scripts`, and the TanStack Devtools panel live there.
- `src/router.tsx` exposes `getRouter()`, the router factory TanStack Start calls. It builds the router context from `getContext()` and wires SSR ↔ TanStack Query via `setupRouterSsrQueryIntegration`. The `declare module '@tanstack/react-router'` `Register` block at the bottom is what makes `Link`/`useParams` etc. type-safe app-wide.
- API endpoints are file routes with a `server.handlers` object, e.g. `src/routes/api/auth/$.ts`. Server-side logic otherwise goes through `createServerFn` from `@tanstack/react-start`.

### Router context / data layer
The router context type is declared in `__root.tsx` (`MyRouterContext`) but *produced* by `getContext()` in `src/integrations/tanstack-query/root-provider.tsx`. Adding anything to the context means editing both. Queries in route `loader`s should go through `context.queryClient` so SSR dehydration works.

### Auth
Better Auth, split across these files:
- `src/lib/auth.ts` — server instance, uses the `tanstackStartCookies()` plugin for Start-native cookie handling.
- `src/routes/api/auth/$.ts` — mounts `auth.handler` at `/api/auth/*`.
- `src/lib/auth-client.ts` — `createAuthClient()` for the browser; `authClient.useSession()` is the session hook (see `src/integrations/better-auth/header-user.tsx`).
- `src/lib/auth-server.ts` — `fetchSession` (a server fn) and `sessionQueryOptions`. `__root.tsx`'s `beforeLoad` resolves it once through the router's `queryClient` and puts `session` on the router context, so `_authed.tsx` guards without an extra round trip. Invalidate `sessionQueryOptions.queryKey` after sign-in/sign-out.
- `src/lib/permissions.ts` — role checks (`requireAdmin`, `requireOwnerOrAdmin`, `ownerScopeFor`).

- `src/lib/permissions-ac.ts` — access-control definitions the `admin()` plugin needs in order to accept `leader` as a role. Application checks live in `permissions.ts`, not here.

**Persisted** via the Drizzle adapter against `src/db/schema/auth.ts` (user/session/account/verification/rate_limit). `role` is a `user_role` pg enum owned by better-auth's `admin()` plugin.

**There is no public sign-up.** `/` is the login page and the only unauthenticated route; accounts are created by an admin through `features/users/create-user` (a `createServerFn` that calls `requireAdmin` and then `auth.api.createUser`). Passwords are never chosen by a human — `@/lib/password.ts` generates one server-side and it is returned to the creating admin exactly once. Bootstrap the first admin by creating a user and promoting it with SQL.

Guards resolve the session with `queryClient.fetchQuery(sessionQueryOptions)`, **not** `ensureQueryData` — the latter returns cached data even once invalidated, so a fresh sign-in reads the pre-login `null` and bounces back to the login page. For the same reason a route `beforeLoad` must not call `router.invalidate()` on a route whose own `beforeLoad` throws a redirect: the interrupt leaves the promise unresolved and the form hangs.

Re-generate the reference schema after adding a plugin with `pnpm dlx auth@latest generate --config src/lib/auth.ts` (note: `@better-auth/cli` is deprecated and emits a schema for an older major).

### Database
Two DB clients exist and they are not interchangeable:
- `src/db/index.ts` — the Drizzle instance (`drizzle-orm/neon-serverless`, Neon's WebSocket `Pool`) bound to `src/db/schema/`. This is the one to use for app queries. **Do not switch it to `drizzle-orm/node-postgres`**: SSR runs on workerd in both `pnpm dev` and production, which has no raw TCP, so `pg` hangs instead of erroring. `neonConfig.poolQueryViaFetch = true` is also required — workerd forbids reusing a socket across request contexts, which otherwise hangs every request after the first.
- `src/db.ts` — a bare `@neondatabase/serverless` HTTP client (`getClient()`), left over from the scaffold.

Schema lives in `src/db/schema/`, one file per table, re-exported from `src/db/schema/index.ts` (Drizzle config points there); `db/init.sql` is only the Neon Launchpad seed script and has drifted from the Drizzle schema. Changing the schema means `db:generate` then `db:migrate` (or `db:push` in dev).

`vite-plugin-neon-new` (wired in `neon-vite-plugin.ts`) auto-provisions and seeds a **claimable Neon database on `pnpm dev` if `DATABASE_URL` is unset — these expire in 72 hours.**

### Environment variables
Two separate mechanisms; pick by where the value is read:
- `src/env.ts` (`@t3-oss/env-core` + Zod) validates `import.meta.env` — client vars must be `VITE_`-prefixed. Import as `import { env } from '@/env'`.
- `process.env.DATABASE_URL` is read directly in `src/db/index.ts`, `src/db.ts`, and `drizzle.config.ts` (the latter loads `.env.local` then `.env` via dotenv).

For production, secrets go in via `wrangler secret put <NAME>`; non-secret vars go in `wrangler.jsonc` under `vars`.

### Deployment
Cloudflare Workers via `@cloudflare/vite-plugin` (`viteEnvironment: { name: 'ssr' }`) and `wrangler.jsonc`, whose `main` points at `@tanstack/react-start/server-entry`. Note the worker is still named `tanstack-start-app` in `wrangler.jsonc`. KV/D1/R2/DO bindings would be added there. Plugin order in `vite.config.ts` matters — `devtools()` must stay first.

## Libraries & Dependencies

The approved stack. Items marked *(not installed yet)* are the designated choice for that role — add them when the need arises rather than picking an alternative.

### Core framework
- **TanStack Start** — full-stack framework (routing, SSR, server functions)
- **TanStack Router** — file-based routing
- **TanStack Query** — server state, caching, mutations
- **TanStack Store** — client-side state (UI state, filters, multi-step form state), kept strictly separate from server state, which lives in TanStack Query only
- **TanStack Table** — member lists, leader capacity tables, review queue. Installed at **v9**, whose API differs from the widely-documented v8: features are declared statically with `tableFeatures({ ... })`, row models come from `create*RowModel()` factories, the hook is `useTable`, `ColumnDef` takes `<typeof features, TData>`, and cells render via `<table.FlexRender cell={cell} />`. `row.getVisibleCells()` needs `columnVisibilityFeature`; use `row.getAllCells()` without it. See `features/users/list-users/Table.tsx`. A v8-compatible shim exists at `@tanstack/react-table/legacy` — prefer the native v9 API for new tables.

### Rules
- Routes never contain logic — they import from `features/` and render.
- Each feature folder maps to one user action, not one entity. e.g. `features/members/create-member/`, not a generic `features/members/`.
- Form-backed feature: `schema.ts`, `schema.test.ts`, `action.ts`, `Form.tsx`, `index.ts`.
- Read/query feature: `action.ts`, `query.ts`, `index.ts`.
- `db/schema/` is organized by table (members, attendance, settings, auth), since multiple features read/write the same tables.
- Testing priority: Zod schemas first, pure lib functions second, mocked server actions third.

### Auth & access control
- Every page except the login page (`routes/index.tsx`) sits under the `_authed` layout route — no page is reachable without a valid session. There is no sign-up route: admins create accounts from the dashboard via `features/users/create-user`.
- Every `action.ts` in `features/` must call a check from `@/lib/permissions.ts` before touching the database. Never rely on the UI hiding a button as the only access control.
- Roles (defined in `@/db/schema/auth.ts`):
  - `admin` — full access: all members, all leaders, settings, review queue, matching runs.
  - `leader` — can only view/act on their own assigned members and their own capacity. Cannot see other leaders' groups or run global matching.
- Webhook routes (`src/routes/api/webhooks/`, `src/routes/api/whatsapp/`) are not session-authenticated — they're verified by a shared secret or signature header instead, since the caller (Google Apps Script, WhatsApp Cloud API) has no user session.
- Never expose a member's full contact/residence detail to a leader who isn't assigned to them, even in list views — filter at the query level in `query.ts`, not by hiding columns in the UI.

## Conventions

- **Import alias**: `@/*` → `src/*` is the only alias — declared in `tsconfig.json` `paths`, resolved by Vite via `resolve: { tsconfigPaths: true }`, and used by `components.json` so the shadcn CLI writes it too. The scaffold's `#`-prefixed subpath import was removed from `package.json`/`tsconfig.json`; don't reintroduce it.
- **Formatting is Biome, not Prettier**: tabs for indentation, double quotes in JS/TS, `organizeImports` on save. Existing scaffold files were generated with 2-space/single-quote style and will be reformatted the first time Biome touches them — that's expected.
- shadcn/ui, `new-york` style, `zinc` base, CSS variables, lucide icons; components land in `src/components/ui/`, utilities via `@/lib/utils` (`cn`). Add components with the CLI rather than hand-writing them.
- TypeScript is strict with `noUnusedLocals`/`noUnusedParameters` and `verbatimModuleSyntax` — use `import type` for type-only imports.
- Tailwind v4: configured entirely through `src/styles.css` (`@tailwindcss/vite`), there is no `tailwind.config`.
